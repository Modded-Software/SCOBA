## 4. Root Causes

### 4.1 Unsafe Player IDs

- Global arrays have 8 slots: indexes `0..7`.
- Playable hero players are `1..6`.
- Global events also fire for player `0` and players `7+`.
- Player `7` exists in map text as Swann's Armory.
- Players `8..15` can also own units.
- Using these IDs as array indexes overruns the arrays.
- This explains the past-end errors.

### 4.2 Wrong Event APIs

- Damage events provide `EventUnitDamageSourcePlayer()` and `EventUnitDamageSourceUnit()`.
- Damage XP currently uses `libNtve_gf_KillingPlayer()` and `libNtve_gf_KillingUnit()`.
- Those are not reliable for non-fatal damage.
- Heal events provide `EventUnitHealLaunchPlayer()`, `EventUnitHealLaunchUnit()`, and `EventUnitHealAmount()`.
- Heal XP currently uses damage APIs:
  - `libNtve_gf_KillingPlayer()`
  - `libNtve_gf_KillingUnit()`
  - `EventUnitDamageAmount()`
- This is invalid in a heal event.

### 4.3 Null Units

- `gv_tPSUNIT[player]` can be null before map init or after invalid setup.
- `gv_TARGET[player]` can be null before a target is set.
- Null values reach:
  - `UnitStatusBarOverride`
  - `UnitGetPosition`
  - `UnitTypeGetName`
  - `UnitGetType`
- These calls can throw runtime errors.

### 4.4 Generated Script Fragility

- `MapScript.galaxy` is generated by the SC2 Editor.
- Direct script edits work at runtime.
- The Editor can overwrite direct script edits on save.
- `Triggers` is the trigger graph source.
- Hand-editing `Triggers` is possible but fragile.

## 5. Intended Behavior Decisions

### 5.1 Healing XP

- User decision: award XP only for healing allies.
- Do not award XP for healing enemies or neutrals.
- User decision: self-healing grants no XP.
- Better implementation uses a global heal event.
- Check `EventUnitHealLaunchPlayer()` is a hero player.
- Check `EventUnitHealLaunchUnit()` belongs to that hero.
- Check the healed unit is an ally.
- Add `EventUnitHealAmount()` to XP.
- Keep heal XP at heal time, unless user changes it.

### 5.2 Damage XP

- User decision: award XP at death.
- Include every hero that contributed damage to the dead unit.
- Attribute contribution at the time of death.
- Do not award XP per damage tick.
- This needs a damage-tracking system.

### 5.3 Death Attribution

- Track damage per victim and per hero player.
- Award contributors when the victim dies.
- A contributor is any hero who dealt damage before death.
- The killing blow should not be the only credit source.
- User decision: split XP proportionally by tracked damage.
- Use the existing 6x damage multiplier.
- Award XP only when the victim dies.
- User decision: summons and companions credit their hero owner.
- User decision: damage to an allied hero grants no XP if it dies.
- Allied hero deaths are ignored.

## 6. Damage Tracking Design

### 6.1 Recommended Record

- Use `UnitGetTag(victim)` as the victim key.
- `UnitGetTag` is unique and is never reused for another unit.
- Store contribution in the global `DataTable`.
- Key format:
  - `dmg:<victimTag>:<player>`
- Store a `fixed` damage total.
- Track heroes `1..6` only.
- Ignore player `0` and player `7+`.

### 6.2 Damage Event

- Register one global `UnitDamaged` trigger with `null` unitref.
- On each event:
  - `victim = EventUnit()`
  - `player = EventUnitDamageSourcePlayer()`
  - `source = EventUnitDamageSourceUnit()`
  - Validate player `1..6`.
  - Validate `source`.
  - Validate victim.
  - Optionally map source owner to hero player.
  - Read old total from `DataTableGetFixed`.
  - Add `EventUnitDamageAmount()`.
  - Write new total.
- `EventUnitDamageAmount()` is actual damage taken.
- Use `EventUnitDamageAttempted()` only if overkill should count.

### 6.3 Death Event

- Register one global `UnitDied` trigger with `null` unitref.
- On death:
  - `victimTag = UnitGetTag(EventUnit())`
  - Loop players `1..6`.
  - Read `dmg:<victimTag>:<player>`.
  - Award XP for each nonzero contribution.
  - Delete all six keys.
  - Clear any extra tracking state.
- Use `UnitIsValid` checks before unit calls.
- Clear records on `UnitRemoved` too.
- Delay removal cleanup by `2.0` game seconds.
- This prevents `UnitRemoved` from clearing records before `UnitDied`.
- This prevents stale records for removed units.

### 6.4 Performance Notes

- DataTable is a string-keyed map.
- One read and one write per damage event is acceptable for this map.
- Six reads per death is cheap.
- Avoid scanning all units on every damage event.
- Avoid one array slot per unit if unit count can grow.
- DataTable avoids fixed-slot exhaustion.
- Delete keys to avoid unbounded table growth.

### 6.5 Precision Notes

- Track `fixed` damage.
- Do not convert to `int` on every event.
- Convert to `int` only for XP grant.
- `fixed` has limited precision.
- Large damage totals may lose precision.
- Cap or split totals if needed.

### 6.6 Edge Cases

- Fatal damage should be tracked before death.
- If fatal damage is not tracked, use `libNtve_gf_KillingPlayer()`.
- Ignore deaths with no hero contribution.
- Ignore non-hero owners.
- Ignore allied players for damage XP.
- Ignore self-damage.
- Ignore damage to allied heroes if the map ever has PvP.
- Handle unit replacement and removal.
- Avoid double awards after `UnitDied` and `UnitRemoved`.

## 7. Full Code Conversion

### 7.1 Is It Possible?

- Yes, map logic can live in handwritten Galaxy.
- The game loads `MapScript.galaxy`.
- The trigger graph is editor metadata; it compiles into script.
- A map can run custom script that is not generated from GUI triggers.
- Custom `.galaxy` files can be included from the map root.
- Include paths are relative to map root and omit `.galaxy`.
- Includes are textual and order-sensitive.
- The map can be treated as code-first.

### 7.2 Recommended Structure

- Keep `MapScript.galaxy` as a small generated bootstrap.
- Put real logic in `scripts/`.
- Example:
  - `scripts/main.galaxy`
  - `scripts/globals.galaxy`
  - `scripts/damage-tracking.galaxy`
  - `scripts/leveling.galaxy`
  - `scripts/ui.galaxy`
- Add one Custom Script element in the Trigger Editor.
- Custom Script content: `include "scripts/main"`.
- Set its initialization function to `main`.
- `main` registers the map-init trigger.
- This survives Editor saves.
- This gives readable, versioned code.

### 7.3 Faster Migration Path

- Copy current generated logic into `scripts/previous.galaxy`.
- Include it from `scripts/main.galaxy`.
- Replace unsafe functions incrementally.
- Delete dead trigger logic after replacement.
- Keep `Triggers` only as reference during migration.
- Do not let the Editor regenerate the old trigger graph after migration.

### 7.4 Risks

- Editor save can overwrite `MapScript.galaxy` if it remains canonical.
- Trigger graph and code can drift if both are edited.
- GUI trigger debugging becomes harder.
- Some editor-only integration may still be useful.
- Full conversion is a refactor, not a small patch.
- Need regression testing for:
  - Map init
  - Hero selection
  - Camera
  - Movement
  - Abilities
  - Dialogs
  - Boss bars
  - Spawns
  - Win conditions

### 7.5 Recommendation

- Use hybrid migration.
- Keep a minimal generated bootstrap.
- Move new logic into `scripts/`.
- Replace trigger-generated combat logic with code.
- Keep data and terrain in the map.
- Do not hand-edit the 1.7 MB `Triggers` file unless necessary.

## 8. C Language Use

- Map logic must run in the Galaxy VM.
- There is no supported C runtime plugin for retail SC2 maps.
- C and C++ can be used for external tools.
- External tools can parse MPQ, stage maps, inspect files, or generate Galaxy.
- DLL injection exists in old community tools, but it is unsupported and risky.
- Do not design map runtime logic around C.
- If C is needed, use it for build and analysis tooling.

- Galaxy global names are case-sensitive.
- `gv_TARGET` is invalid; the declared array is `gv_tARGET`.
